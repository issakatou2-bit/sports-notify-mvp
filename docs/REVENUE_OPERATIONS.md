# 最初の収入を作る運用

開始: 2026-09-06。ユーザーの「収益をあげていく仕組みを実装、動いてください」に対応。
紹介経路と小口制作を開始する。売上発生・報酬確定・入金・利益は別に確認する。

## 公開する導線

- `https://collespo.com/watch-champions-league.html`：公式情報で契約の選び方を説明。既存WOWOW広告は月額プランの案内にだけ配置。シーズンパスの成果対象性は未確認なので、パスは公式情報へ直接案内する。
- `https://collespo.com/services.html`：PNG3枚・同一デザイン・1チーム1試合・修正1回・税込3,000円。見本は架空のチーム/試合と明記。個別相談で受付、納期と決済方法は注文確定前に合意する。
- ホームのメニュー/下部と運営者情報から接続。サイト専用の `deploy_site.yml` で公開する。日次の動画・SNS・通知の実行は不要。
- 相談フォームはメール本文の作成のみ。実際の送信は利用者のメールアプリで行う。ブラウザに送信成功表示を出さない。問い合わせの実受信は別途確認が必要。

## 初回注文への手順

1. ココナラなどの販売アカウントを運営者本人が登録し、受取設定を完了する。勝手に個人情報や本人確認書類を登録しない。登録まではサイトのメール相談を入口にする。
2. 下の出品文と公開見本を使い、対応枠はまず1件。納期は運営者の稼働と素材が揃う日を確認して設定する。実績・経験年数・納品速度を捏造しない。
3. 公開した販売URLをサイトの相談欄に追加する。プラットフォーム経由の相談はその中で取引を続ける。
4. 相談が来たら用途、素材、掲載許可、修正範囲、納期、総額、支払時期、キャンセル条件を確認する。直接販売を選ぶ場合は販売者表示など必要な準備を先に整える。
5. 制作した3枚を目視確認し、顧客確認後に納品。作業開始/終了の時間を台帳へ記録する。

## 出品文（登録後に使う下書き、まだ出品していない）

タイトル：スポーツチームの試合告知・結果画像を3枚作ります

地域のスポーツチームの広報担当者向けに、SNSに載せる画像を制作します。
試合告知・試合結果・次回予告を揃ったデザインにしたい方に。

税込3,000円で、同一デザインのPNG画像3枚（1080×1350px）を制作します。
対象は1チーム・1試合を中心にした内容です。納品前の修正1回を含みます。
チーム名、対戦相手、日時、会場、確定した結果、希望の色をご用意ください。
写真やロゴはなくても作れます。使用する場合は掲載許可を得た素材に限ります。

ロゴ制作、撮影、情報の取材・収集、投稿代行、別サイズ、編集用データは含みません。
対応可否と納期を先に確認したいので、購入前に用途と希望日をお知らせください。
見本は架空のチーム・試合の制作例で、取引実績ではありません。

## 制作を再現する

`scripts/render_team_cards.py` は外部APIなしで3枚を生成する。Pillowと日本語フォントが必要。
`docs/team_cards_sample.json` を `build/customer-private/` に複製して顧客から確認済みの内容を入力。
`sample: false` は実納品時だけ指定。顧客入力・納品画像はweb/やdata/へ置かない。

```text
python scripts/render_team_cards.py --input build/customer-private/order-001.json --font C:/Windows/Fonts/meiryo.ttc --out-dir build/customer-private/order-001
```

生成だけでは納品完了としない。表記・日時・会場・スコア・文字切れ・素材の掲載許可を確認する。
チーム名等が長すぎる場合はエラーにする。文字を詰めて無理に納品せず、表記を相談する。

## 反応と収支の記録

制作受付URLの `?from=home|about|watch|youtube|bluesky|tiktok|threads|podcast` を相談メールに引き継ぐ。
これは「受信した相談の案内元」であり、訪問者数・クリック数を取得する機能ではない。
未知の値はdirect。顧客の入力を追跡サービスに送らず、端末にも自動保存しない。

`scripts/revenue_report.py --init` で非公開の `build/revenue-private/ledger.json` を初期化できる。
既存ファイルは上書きしない。以後 `scripts/revenue_report.py` で集計する。
build/はgit対象外。顧客の氏名・メール・口座番号を共有文書や台帳に転記せず、相談IDで参照する。

台帳の例（架空の記録、実績ではない）：

```json
{
  "version": 1,
  "orders": [{"id": "order-001", "date": "2026-09-06", "source": "home", "status": "pending", "gross_yen": 3000, "fee_yen": 0, "refund_yen": 0, "labor_minutes": 0}],
  "expenses": [],
  "cash": []
}
```

- orders：1取引1行を更新する。inquiry=相談中、pending=注文/成果の確定待ち、confirmed=確定、canceled=未確定の取消。inquiriesは現在相談中の件数。完了済みを含む累計相談数ではない。
- 確定後の返金はconfirmedのままrefund_yenへ。fee_yenは実際に負担した販売手数料。未確定の費用はexpensesへ記録する。
- expenses：id/date/yen。決済/振込手数料をordersと二重計上しない。記録済み制作費・振込費用を含め、非負の円額を記録する。
- cash：id/date/yen。実際の入金額を正、口座からの返金を負で記録。手数料差引後の入金に再度手数料を引かない。ここは売上入金の記録で、口座残高ではない。
- contribution_yen=確定売上−返金−販売手数料−記録済み費用。共通固定費・労働・税が未記録なら除外されたまま。会計/申告ソフトではない。
- A8は未確定をpending、確定した報酬をconfirmedで記録。表示の税込/税抜を揃えて転記し、レポート表示額と銀行着金を混同しない。実績の出典は非公開メモに保持する。

## 最初の2週間で見ること

- A8：同一の期間・絞り込みで表示、クリック、発生、確定、入金を別々に記録。本人のテストクリックや自己申込を成果づくりに使わない。公開した広告掲載URLの提出も確認する。
- 制作：相談の件数・案内元、受注、断られた理由、作業分数、手数料差引額。まず1件を終えてから価格や枚数を変える。
- 閲覧が少ない段階で「価格が悪い」と決めない。問い合わせがあるのに売れない場合は、用途・見本・日程・価格のどこで止まったかを確認する。
- 営業文は相手に合わせて用意する。外部へのメール/DM送信は、宛先と内容についてユーザーの明示許可を得てから行う。
- この文書の運用周期は提案であり、定期実行の予約を作成したものではない。
