# コレスポ型の骨組み

毎日「今日のどれを見るべきか」を、理由つきで複数のチャンネルへ自動で出す。
コレスポはMLBと欧州サッカーで動いているが、仕組み自体はジャンルに依存しない。

このドキュメントは、別ジャンルへ移すときに
**どこを差し替え、どこをそのまま使うのか**を示す。

どのジャンルが向いているかは `scripts/genre_fit.py` で採点できる。

```bash
python3 scripts/genre_fit.py
```

---

## 1. 全体の形

```
 [1] 収集      公開APIから、その日のデータを取る
       ↓
 [2] 選定      候補に点をつけ、上位を選ぶ            ← ジャンル固有
       ↓
 [3] 理由づけ  なぜ選ばれたかを、データから文にする   ← ジャンル固有
       ↓
 [4] 生成      動画 / 画像 / HTML / 音声を作る        ← 使い回せる
       ↓
 [5] 配信      YouTube / Bluesky / Push / サイト      ← 使い回せる
       ↓
 [6] 答え合わせ 予告した試合が実際どうだったかを翌週出す
```

これと**並走する2本**がある。日次とは独立に動く。

```
 [A] 資産      日付に依存しない在庫(用語・一覧・歴史)
 [B] 別軸      検証できない情報(現地の反応の和訳)を、事実と混ぜずに出す
```

---

## 2. 層ごとの中身

### [1] 収集

| 対象 | ソース | 費用 | 制限 |
|---|---|---|---|
| MLB | statsapi.mlb.com | 無料・キー不要 | 実質なし |
| 欧州サッカー | football-data.org | 無料 | 10req/分・個人成績なし |
| 現地の注目度 | YouTube Data API | 無料 | 10,000ユニット/日 |
| 現地の話題量 | RSS (Reddit / ESPN / 公式) | 無料 | 429に注意 |

**移すときに確認すること**（順に潰す。上で詰まったら下は無意味）

1. 認証なし、または無料枠で毎日叩けるか
2. 返ってくるのは「日程」だけか、「成績」まで来るか
   → 成績が来ないと [3] の理由づけが薄くなる。サッカーがこの状態。
3. 固有名詞の表記が、こちらの名簿と一致するか
   → **ここは必ずズレる。** 後述。

### [2] 選定

やることは1つ。候補ごとに点をつけて並べる。

```python
W_JP_PLAYER      = 30.0   # 日本人選手が出る
W_DIVISION_LEAD  = 25.0   # 首位攻防
W_RIVALRY        = 20.0   # 伝統の一戦
W_STREAK         = 15.0   # 連勝中
```

重みは「日本語圏の視聴者にとって何が引きになるか」で決める。
**現地の重みとは違う。** MLBで日本人選手に30点を置くのは、
現地の注目度とは無関係に、日本語圏では最大の引きだから。

移すときは、この表を書き換えるだけでよい。構造は共通。

### [3] 理由づけ

2段構え。

- **ルールベース**（常に動く）: 順位・成績・日程から機械的に文を組む
- **AI**（任意）: Haiku 4.5で解説文とフック文に整える

AIが落ちても配信は止まらない。ただし**黙って落ちさせない** —
`ai_status` を出力に持たせ、GitHub Actions の `::error::` で見えるようにする。

> 一度、AIの出力が `max_tokens` で切れて
> 「防御率2.41の投」という文が通知とBlueskyと動画にそのまま流れた。
> 静かに壊れる経路は、必ず見えるようにしておくこと。

### [4] 生成

**ここから下はジャンルに依存しない。** そのまま使える。

| 出力 | 実装 |
|---|---|
| 縦動画(ショート) | PIL でフレーム描画 → ffmpeg に rawvideo で流す |
| 横動画(週次) | 同上 |
| 音声 | VOICEVOX (Docker, speaker 3) |
| サムネイル | PIL |
| サイト | Python で静的HTML生成 |

### [5] 配信

YouTube / Bluesky / Web Push / サイト / RSS。
投稿本文の組み立ては `scripts/post_common.py` に寄せてあり、
`max_chars` だけ変えれば各媒体に合う。

### [6] 答え合わせ

予告した試合が実際にどうなったかを、翌週に出す。
これは他所が持っていない。**予告だけなら誰でも出せるが、
「当たったかどうか」を出すには、予告を保存していないとできない。**

## 3. 並走する2本

### [A] 資産

日付に依存しない在庫。現在19本＋サッカー5本。

- 用語・略称の解説
- 一覧もの（球場・ライバル関係・日本人選手）
- 比較もの（MLBとNPBの違い）

役割が3つある。

1. オフシーズンに出すものが無くなるのを防ぐ
2. 検索から入ってくる（「OPSとは」で来た人に同じ説明の動画）
3. 日次が壊れた日の保険

### [B] 別軸

現地のファンが何と言っているか、を和訳して出す。

**これは事実の提示とは別枠にする。** 混ぜない。
画面の背景色を変え、動画も分け、コーナーとして切る。

> 翻訳を通した時点で、こちらの解釈が入る。
> 数字は誰でも同じものを確認できるが、和訳は確認できない。
> だから「検証できないから出さない」ではなく、
> **「別の軸として、そういうものとして出す」**。

## 4. 移植のとき必ず踏む地雷

実際に踏んだものだけを書く。

### 4.1 固有名詞は一致しない

名簿に `"Bayern Munich"` と書き、APIが返すのは `"FC Bayern München"`。
完全一致で照合していたため、**20クラブ中1つしか当たっていなかった。**

しかもオフシーズンは試合が0件なので、疎通確認では表面化しない。
開幕日に「日本人選手が1人も検出されない」という形で出るところだった。

対策:

- 照合用のキーを別に持つ（表示用の名前と分ける）
- 正規化（小文字化・記号除去・ダイアクリティカルマーク除去）してから部分一致
- キーはリーグ内で一意な語を選ぶ
  （`borussia` はドルトムントと衝突するので `monchengladbach`）
- **APIキーが無くても走るテストを書く** → `scripts/test_club_match.py`

同じ問題はMLB側でも起きた。`"Dodger Stadium"` で引いていたが、
APIは `"UNIQLO Field at Dodger Stadium"` を返していた。

### 4.2 原稿と画面が別々にデータを見ると必ずズレる

音声の原稿を作る処理と、画面を描く処理が、それぞれ別々に項目リストを
組み立てていた。片方にだけ項目を足したら、画面側が範囲外で落ちた。

**週次動画で直したのに、資産動画で同じことを繰り返した。**

対策: `list_items()` のような単一の関数を通す。加工はそこだけで行う。

### 4.3 尺を時間で決めると無音で埋まる

週次動画を「8分」と決めて作ったら、**53%が無音**になった。
音声が足りないぶんを、そのまま黙って引き伸ばしていた。

対策: 尺は `音声の長さ + 余白` で決める。長さは結果であって目標ではない。

内容を増やして無音は13%まで下がったが、そもそも
**視聴維持率と動画の長さの相関は -0.22 しかなかった。**
長さは問題ではなかった。

### 4.4 冒頭が全て

同じ内容で、冒頭の1文を変えただけで視聴維持率が
**15.5% → 35.3% → 102.7%** と動いた。平均4.5倍。

「今日の注目試合をお届けします」ではなく、
「大谷翔平が2試合連続でホームランを打っています」から始める。

日次動画のフック選定は優先順で決める。

```
log_notes → 連続記録 → 日本人先発 → 首位攻防(ゲーム差つき)
          → 通知フック → 日本人選手 → 汎用
```

### 4.5 1本に詰めると全部薄くなる

選手成績と現地の注目度を1本にまとめたら76秒・7画面になり、
主題が3つ混ざった。タイトルもサムネイルも1つしか表せない。

**実際、最も見られた動画は単一主題のもので、
情報を詰めたものほど視聴率が落ちていた。**

対策: 2本に分けて、それぞれ主題を1つにする。

### 4.6 定説は測ると外れる

球場ごとの得点を実測したら、
**クアーズ・フィールドは1位ではなく2位**、
**フェンウェイ・パークは打者有利とされるのに25位**だった。

「〜とされます」と書く前に、手元のデータで確かめる。
確かめられるなら、定説ではなく実測を出す。

### 4.7 スケジュールは現地時間で考える

日本時間8時に「昨夜の結果」を出す設定にしていたが、
**その時刻はまだ1試合も終わっていなかった。**

```
東部 19:00開始 → JST 08:00開始 / 11:00終了
太平洋 19:00開始 → JST 11:00開始 / 14:00終了
```

全試合が出揃うのはJST 14時。16時に変更した。

また、GitHub の `schedule` は数時間遅れる。
分単位の正確さが要る配信は外部トリガ（cron-job.org）から叩く。

### 4.8 1本の失敗で全部止めない

資産動画を全トピック作るループで、1本が失敗した時点で
以降が丸ごと未処理になっていた。

対策: `set +e` にして、段階ごとに終了コードを見て次へ進む。
最後に失敗した分をまとめて出す。

## 5. 差し替え表

移植するとき、実際に触るファイル。

| 層 | 差し替える | そのまま使う |
|---|---|---|
| 収集 | `notability_engine.py` の fetch 関数 | リトライ・レート制限の処理 |
| 選定 | 重みの定数、`Game`/`Standing` の詰め方 | 点をつけて並べる構造 |
| 理由づけ | 名簿、用語テーブル、プロンプト | AI呼び出しとフォールバック |
| 生成 | 見出しの文言 | 描画・音声・サムネイルの全て |
| 配信 | タグ、説明文のテンプレ | 投稿処理の全て |
| 資産 | `LIST_TOPICS` の中身 | トピックの枠組み |

**書き換える量はだいたい `notability_engine.py` の上半分だけ。**
`scripts/` の下はほぼそのまま動く。

## 6. 移植の順番

1. **データが取れるか確かめる。** ここで詰んだら他は無意味。
2. **名簿を作り、照合テストを書く。** APIキー無しで走るもの。
3. 選定の重みを決める。まず3〜4項目でよい。
4. 日次を1本通す。サイトと通知まで。
5. 動画を足す。
6. 資産動画を数本作る。オフの在庫と検索の入口。
7. アナリティクスを見て、冒頭の文を直す。**ここが一番効く。**

1〜4が動くまで、5以降には手を出さないこと。
